    5. Kapitel 4 - Der Flutter-Client für die Anwendung RdvMedecins

    5.1. Überblick über die Architektur

    Dieser Client kommuniziert mit dem [rdvmedecins-nestjs-server]-Server des Kurses – der unverändert bleibt – über dieselben HTTP-Routen, die bereits dokumentiert wurden (POST [/login], GET [/getAllDoctors], GET [/getAllClients], GET [/getDoctorScheduleOfDay/:doctorId/:day], POST [/addAppointment], POST [/deleteAppointment]), mit demselben JSON-Umschlag [{ status, data }] und derselben tokenbasierten Authentifizierung [JWT] (Header [Authorization: Bearer <token>]). Bei dieser Variante erhält die Gesamtarchitektur eine dritte Komponente: Je nach gewähltem Kompilierungsziel (siehe Kapitel 5) führt nicht mehr nur ein Browser den Client aus, sondern möglicherweise ein mobiles oder ein Desktop-Betriebssystem, das den kompilierten [Dart]-Code direkt ausführt – der Server [NestJS] verarbeitet unterdessen weiterhin nur dieselben HTTP-Anfragen, unabhängig vom Ziel.

    // =========================================================================
// main.dart
// -------------------------------------------------------------------------
// Einstiegspunkt des Flutter-Clients. Äquivalent von src/main.ts auf der Vue.js-
// Client-Seite dieses Kurses: Diese Datei startet die Anwendung explizit
// (hier runApp(...); auf der Vue.js-Seite createApp(...).mount(...)) UND
// konfiguriert sie.
//
// Vue.js konfiguriert seine Anwendung mit app.provide(key, value), direkt auf der
// Anwendungsinstanz aufgerufen - Flutter/provider verwendet
// stattdessen ein Widget, MultiProvider, das an der Wurzel des Baums platziert wird (siehe runApp(...)
// weiter unten): Jeder darin enthaltene ChangeNotifierProvider/Provider stellt
// eine Instanz für den GESAMTEN Teilbaum bereit, den er umschließt, genau
// wie app.provide(...) es für alle untergeordneten Komponenten tat -
// dieselbe Idee, ausgedrückt als WIDGET statt als imperativer
// Methodenaufruf, denn in Flutter ist ALLES ein Widget (auch
// die Konfiguration eines gemeinsamen Zustands).
//
// Die REIHENFOLGE der Konstruktionen ist weiterhin wichtig, aus denselben Gründen wie
// auf der Vue.js-Seite: AuthService(settings) braucht ein bereits existierendes settings
// (um apiBaseUrl zu lesen); AppointmentService braucht authHttp UND settings.
//
// WICHTIGER UNTERSCHIED zu Vue.js: createAuthStore(settings) und
// createLanguageStore() auf der Vue.js-Seite lesen localStorage SYNCHRON
// während ihrer Konstruktion, noch vor dem ersten Rendern. Ihre
// Flutter-Entsprechungen (AuthService.init(), TranslationsService.init())
// sind ASYNCHRON (siehe die jeweiligen Dateien): main() selbst muss
// daher eine async-Funktion werden und auf diese beiden
// Initialisierungen WARTEN (await), BEVOR runApp(...) aufgerufen wird - andernfalls würde der erste
// angezeigte Bildschirm eine eventuell bereits gespeicherte Sitzung oder Sprache ignorieren,
// solange shared_preferences noch nicht geantwortet hat.
//
// Wie die Angular-, React- und Vue.js-Clients dieses Kurses (eine einzige Seite,
// keine Routing-Tabelle) verwendet dieser Flutter-Client NUR die minimale
// Navigation von MaterialApp (unverzichtbar für showDialog(), siehe
// features/booking_dialog/booking_dialog.dart): AppRoot (siehe app.dart)
// zeigt je nach AuthService.isLoggedIn entweder den Anmeldebildschirm oder den Rest der Anwendung an
// - ein einfaches Dart-if/else genügt, ein Routing-Paket
// (go_router oder ein anderes) hätte für eine Anwendung
// mit nur einem Bildschirm nichts gebracht.
// =========================================================================

import 'package:flutter/material.dart';
import 'package:provider/provider.dart';

import 'app.dart';
import 'core/http/auth_http_client.dart';
import 'core/i18n/translations_service.dart';
import 'core/services/auth_service.dart';
import 'core/services/appointment_service.dart';
import 'core/services/settings_service.dart';

Future<void> main() async {
  // WidgetsFlutterBinding.ensureInitialized(): unverzichtbar, sobald man
  // eine Flutter-API VOR runApp(...) aufruft (hier shared_preferences und
  // rootBundle.loadString(...) in TranslationsService.init()) - ohne
  // diese Zeile würden diese Aufrufe beim Start fehlschlagen. Vue.js kennt nichts
  // Vergleichbares: Der Browser ist immer "bereit", noch bevor
  // src/main.ts ausgeführt wird.
  WidgetsFlutterBinding.ensureInitialized();

  // 1. Zuerst SettingsService: AuthService und AppointmentService brauchen ihn
  //    (apiBaseUrl).
  final settings = SettingsService();

  // 2. AuthService: erhält settings direkt im Konstruktor, wie
  //    createAuthStore(settingsStore) auf der Vue.js-Seite - anschließend stellt init() eine
  //    eventuell gespeicherte Sitzung wieder her (siehe den Kopfkommentar
  //    oben zur Asynchronität dieses Schritts).
  final auth = AuthService(settings);
  await auth.init();

  // 3. die authentifizierte HTTP-Schicht, dann der Geschäftsservice - beide
  //    HIER gebaut, nur einmal, statt innerhalb eines Widgets
  //    (wo sie bei jedem Rendern neu gebaut würden): genau dasselbe
  //    Prinzip wie createSettingsStore()/createAuthStore(...), die auf der Vue.js-Seite nur
  //    einmal vor app.mount(...) aufgerufen werden.
  final authHttp = AuthHttpClient(auth);
  final api = AppointmentService(authHttp, settings);

  // 4. TranslationsService: lädt das Start-Wörterbuch (die
  //    gespeicherte Sprache oder standardmäßig die Sprache des Geräts) - KEINE Reihenfolgeabhängigkeit
  //    von den vorherigen Schritten (anders als
  //    createLanguageStore() auf der Vue.js-Seite, das auf
  //    app.use(i18n) warten musste: Diese Datei implementiert alles selbst, siehe
  //    core/i18n/translations_service.dart, es muss also kein
  //    Plugin eines Drittanbieters installiert werden, bevor man es verwenden kann).
  final translations = TranslationsService();
  await translations.init();

  runApp(
    // MultiProvider: fasst mehrere Provider in einem einzigen Widget zusammen,
    // statt sie von Hand zu verschachteln (Provider(...) > Provider(...)
    // > Provider(...) > ...) - eine Lesbarkeit, vergleichbar mit der Abfolge
    // der Aufrufe "app.provide(SettingsKey, ...); app.provide(AuthKey, ...);
    // app.provide(LanguageKey, ...);" auf der Vue.js-Seite, trotz des Unterschieds
    // in der Form (eine Liste von Widgets statt einer Folge von Anweisungen).
    MultiProvider(
      providers: [
        // .value(...) statt Provider(create: ...): Diese Instanzen
        // existieren bereits (oben gebaut) - .value(...) stellt sie lediglich
        // dem Widget-Baum bereit, ohne
        // neue zu bauen. ChangeNotifierProvider abonniert zudem
        // notifyListeners() und zeichnet automatisch jedes
        // Widget neu, das context.watch<...>() auf diesem Provider aufgerufen hat (siehe
        // lib/app.dart) - die Rolle, die auf der Vue.js-Seite die "reaktive" Natur eines
        // reactive(...) spielt.
        ChangeNotifierProvider.value(value: settings),
        ChangeNotifierProvider.value(value: auth),
        ChangeNotifierProvider.value(value: translations),
        // AppointmentService ist KEIN ChangeNotifier (in diesem Service ändert sich nach dem Bau
        // nichts mehr im Lauf der Zeit): Ein einfacher Provider
        // genügt, er stellt nur diese Instanz bereit, ohne
        // jeden Benachrichtigungsmechanismus.
        Provider.value(value: api),
      ],
      child: const RdvMedecinsApp(),
    ),
  );
}

    Kommentieren wir diesen Code:

    • Zeile 60: [WidgetsFlutterBinding.ensureInitialized();] – erforderlich, sobald Sie eine [Flutter]-API VOR [runApp(...)] aufrufen (hier [shared_preferences] und [rootBundle.loadString(...)]) – ohne diese Zeile würden diese Aufrufe beim Start fehlschlagen; [Vue.js] muss nichts Derartiges berücksichtigen, da der Browser stets „bereit“ ist, noch bevor [src/main.ts] ausgeführt wird.
    • Zeilen 70–71: [final auth = AuthService(settings); await auth.init();] – GROSSER UNTERSCHIED zu [createAuthStore(settingsStore)] auf der Seite von [Vue.js], das [localStorage] SYNCHRON liest, sobald es erstellt wird: [AuthService.init()] ist ausdrücklich [async], und [main()] muss daher selbst ebenfalls asynchron sein, um vor [runApp(...)] WARTEN zu können – andernfalls würde der erste angezeigte Bildschirm eine bereits gespeicherte Sitzung ignorieren, während er auf die Antwort von [shared_preferences] wartet.
    • Zeile 89: [await translations.init();] – derselbe Hinweis wie oben zur gespeicherten Sprache; anders als [createLanguageStore()] bei [Vue.js], das auf [app.use(i18n)] warten musste, hat dieser Schritt keine sequenzielle Abhängigkeit von den vorherigen: [TranslationsService] implementiert alles selbst, ohne dass vorher ein Drittanbieter-Plugin installiert werden müsste.
    • Zeilen 98–116: [MultiProvider(providers: [...], child: const RdvMedecinsApp())] – das Pendant, in Form eines WIDGETS statt imperativer Aufrufe, zur Sequenz [app.provide(SettingsKey, ...); app.provide(AuthKey, ...); app.provide(LanguageKey, ...);] auf der Seite von [Vue.js]: Jeder [ChangeNotifierProvider.value(...)] stellt eine vorab erstellte Instanz dem gesamten Teilbaum zur Verfügung.

// app.dart
// -------------------------------------------------------------------------
// Port von src/app/App.vue (Vue.js-Client dieses Kurses): das ROOT-
// Widget der Anwendung (von lib/main.dart gebaut). Wie in den
// drei anderen Varianten dieses Kurses spielt es die Rolle des
// "Dirigenten": Es hält den Anwendungszustand (Ärzte, Clients,
// angezeigter Terminkalender, zuletzt gesuchter Arzt/Tag...) und reagiert auf die Aktionen
// der "Geschäfts"-Widgets in lib/features/, um den NestJS-Server im
// richtigen Moment über AppointmentService aufzurufen.
//
// Seit der Einführung der Authentifizierung spielt dieses Widget zudem die Rolle des
// "Guards": Solange AuthService.isLoggedIn false ist, zeigt es nur
// LoginPage an (siehe lib/features/login/); da alle Server-Routen
// durch JwtAuthGuard geschützt sind, wäre es ohnehin nutzlos (und eine Quelle
// von 401-Fehlern), Ärzte/Clients/Terminkalender zu laden, bevor man angemeldet ist.
//
// Zwei Klassen, wie in den anderen "zustandsbehafteten" Dateien dieses Clients:
// RdvMedecinsApp (die MaterialApp - die ABSOLUTE Wurzel, siehe lib/main.dart) und
// AppRoot/_AppRootState (das eigentliche Äquivalent von App.vue, mit seinem gesamten Zustand).
// =========================================================================

import 'package:flutter/material.dart';
import 'package:provider/provider.dart';

import 'core/i18n/translations_service.dart';
import 'core/models/appointment_models.dart';
import 'core/services/auth_service.dart';
import 'core/services/appointment_service.dart';
import 'core/services/settings_service.dart';
import 'features/schedule/schedule_view.dart';
import 'features/booking_dialog/booking_dialog.dart';
import 'features/doctor_day_picker/doctor_day_picker.dart';
import 'features/login/login_page.dart';

// -------------------------------------------------------------------------
// RdvMedecinsApp: die Flutter-Wurzel im strengen Sinn - MaterialApp liefert

class _AppRootState extends State<AppRoot> {
  // — Anwendungszustand —————————————
  // das direkte Äquivalent der ref(...) von App.vue, als einfache
  // veränderliche Felder von _AppRootState: setState(...) (siehe die Methoden
  // unten) ersetzt die automatische Reaktivität von Vue.js.
  List<Doctor> _doctors = [];
  List<Client> _clients = [];
  DoctorDaySchedule? _schedule;
  String? _error;

  // Die letzte Suche (Arzt + Tag) wird gemerkt, um den Terminkalender nach einer Buchung oder einer Stornierung
  // aktualisieren zu können - dieselbe
  // Rolle wie lastDoctorId/lastDay auf der Vue.js-Seite.
  int? _lastDoctorId;
  String? _lastDay;

  // dauerhaft gehaltene Referenz auf AuthService, um sich in dispose() sauber
  // abmelden zu können (siehe unten) - den Grund für diese Wahl nennt
  // der Kommentar von initState() weiter unten.
  late final AuthService _auth;

  @override
  void initState() {
    super.initState();
    // context.read<AuthService>(): Wenn initState() läuft, ist das
    // Widget bereits ordnungsgemäß in den Baum eingefügt (anders als im
    // Konstruktor, wo context noch nicht für
    // Dependency Injection verwendet werden kann) - aber context.watch(...) wird hier NICHT verwendet:
    // Ein StatefulWidget darf einen Provider nur einmal abonnieren,
    // explizit, niemals innerhalb von initState() mit watch()
    // (das einen Build-Kontext voraussetzt). Daher wird die Referenz in
    // einem Feld (_auth) gehalten, und wir abonnieren selbst mit addListener(...).
    _auth = context.read<AuthService>();
    _auth.addListener(_onAuthChange);

    // Äquivalent von "watch(() => auth.isLoggedIn, ..., { immediate: true })"
    // auf der Vue.js-Seite: { immediate: true } löst den Callback
    // SOFORT aus, ohne auf eine erste Änderung zu warten - nützlich, falls bereits eine Sitzung
    // gespeichert war (siehe AuthService.init(), das von
    // lib/main.dart vor runApp(...) abgewartet wird). Vue.js bietet diese Option
    // direkt an; Flutter hat in addListener(...) keinen
    // eingebauten entsprechenden Mechanismus, daher wird derselbe Effekt VON HAND nachgebildet: ein
    // expliziter Aufruf direkt nach dem Abonnieren, zusätzlich zum Abonnement
    // selbst.
    if (_auth.isLoggedIn) {
      _loadInitialLists();
    }
  }

  @override
  void dispose() {
    // Das Abmelden ist hier ESSENZIELL: Ohne es würde _onAuthChange
    // weiter aufgerufen, nachdem dieses Widget zerstört wurde (zum
    // Beispiel bei einem Hot Reload oder einem Routenwechsel), und
    // würde beim ersten setState(...) auf einem
    // nicht eingebundenen Widget eine Exception auslösen. Vue.js kennt hier nichts Vergleichbares: watch(...) wird
    // automatisch "aufgeräumt", wenn die Komponente, die es erzeugt hat, zerstört wird.
    _auth.removeListener(_onAuthChange);
    super.dispose();
  }

  void _onAuthChange() {
    if (_auth.isLoggedIn) {
      _loadInitialLists();
    }
  }

  // -----------------------------------------------------------------------
  // Wenn wir angemeldet sind (erfolgreiche Anmeldung oder aus
  // shared_preferences wiederhergestellte Sitzung), werden die Listen der Ärzte und Clients
  // ein für alle Mal geladen.
  // -----------------------------------------------------------------------
  void _loadInitialLists() {
    final api = context.read<AppointmentService>();
    api.getAllDoctors().then((result) {
      if (mounted) setState(() => _doctors = result);
    }).catchError((Object err) {
      if (mounted) setState(() => _error = err.toString());
    });
    api.getAllClients().then((result) {
      if (mounted) setState(() => _clients = result);
    }).catchError((Object err) {
      if (mounted) setState(() => _error = err.toString());
    });
  }

  // -----------------------------------------------------------------------
  // reagiert auf den Button "Log out": löscht die Sitzung UND den angezeigten Geschäftszustand - ohne dies
  // würde ein danach angemeldeter neuer Benutzer kurzzeitig
  // den Terminkalender des vorherigen sehen.
  // -----------------------------------------------------------------------
  Future<void> _onLogout() async {
    await _auth.logOut();
    setState(() {
      _doctors = [];
      _clients = [];
      _schedule = null;
      _error = null;
      _lastDoctorId = null;
      _lastDay = null;
    });
  }

  // -----------------------------------------------------------------------
  // reagiert auf den Aufruf von onSearch(...) durch das Widget DoctorDayPicker
  // -----------------------------------------------------------------------
  void _onSearchSchedule(int doctorId, String day) {
    setState(() {
      _error = null;
      _lastDoctorId = doctorId;
      _lastDay = day;
    });
    _loadSchedule();
  }

  // -----------------------------------------------------------------------
  // reagiert auf den Aufruf von onBook(...) durch das Widget ScheduleView: HIER wird, anders als bei
  // Vue.js (das lediglich das Fenster öffnete,
  // während es slotBeingBooked merkte), das Dialogfeld DIREKT
  // mit showDialog (über openBookingDialog(...)) geöffnet und sein Ergebnis
  // ABGEWARTET - Details zu diesem strukturellen Unterschied siehe
  // den Kopf von booking_dialog.dart.
  // -----------------------------------------------------------------------
  Future<void> _onBookingRequest(SlotJson slot) async {
    final lastDay = _lastDay;
    if (lastDay == null) {
      return;
    }
    final clientId = await openBookingDialog(context: context, slot: slot, clients: _clients);
    if (clientId == null) {
      return; // Der Benutzer hat das Dialogfeld geschlossen, ohne einen Patienten zu wählen
    }
    try {
      await context.read<AppointmentService>().addAppointment(lastDay, clientId, slot.id);
      _loadSchedule(); // Der Terminkalender wird aktualisiert: Der Slot erscheint nun als gebucht
    } catch (err) {
      if (mounted) setState(() => _error = err.toString());
    }
  }

  // -----------------------------------------------------------------------
  // reagiert auf den Aufruf von onCancel(...) durch das Widget ScheduleView
  // -----------------------------------------------------------------------
  Future<void> _onCancelAppointment(AppointmentJson appointment) async {
    try {
      await context.read<AppointmentService>().deleteAppointment(appointment.id);
      _loadSchedule(); // Der Terminkalender wird aktualisiert: Der Slot ist wieder frei
    } catch (err) {
      if (mounted) setState(() => _error = err.toString());
    }
  }

  void _loadSchedule() {
    final doctorId = _lastDoctorId;
    final day = _lastDay;
    if (doctorId == null || day == null) {
      return;
    }
    context.read<AppointmentService>().getDoctorScheduleOfDay(doctorId, day).then((result) {
      if (mounted) setState(() => _schedule = result);
    }).catchError((Object err) {
      if (mounted) setState(() => _error = err.toString());
    });
  }

// -------------------------------------------------------------------------
// Port von core/models/appointment.models.ts (Vue.js-Client dieses Kurses), das seinerseits
// unverändert aus den Angular- und React-Clients kopiert wurde: die Dart-Klassen, die
// die Form der vom NestJS-Server empfangenen JSON-Daten beschreiben. Wie ihre
// TypeScript-Gegenstücke hängen diese Klassen von keinem UI-Framework ab
// (hier kein Flutter-Import) - das ist "reines" Dart, so wie
// appointment.models.ts "reines" TypeScript war.
//
// STRUKTURELLER UNTERSCHIED zu TypeScript: Ein TypeScript-"interface" ist
// eine bloße Beschreibung einer FORM, die nur zur Kompilierzeit geprüft wird -
// zur Laufzeit wird ein dekodiertes JSON-Objekt (JSON.parse) UNVERÄNDERT verwendet,
// ohne Umwandlung, und TypeScript "vertraut" dem Entwickler (siehe das
// "as ServerResponse<T>" in appointment.service.ts). Dart kennt keinen solchen Begriff impliziter
// struktureller Typisierung: jsonDecode(...) liefert immer dynamische
// Typen (Map<String, dynamic>, List<dynamic>...), die
// explizit über einen Konstruktor fromJson(...) in Instanzen von Dart-Klassen umgewandelt werden müssen -
// vorhanden in JEDER der folgenden Klassen. Das ist einmalig aufwendiger zu schreiben,
// aber die Umwandlung wird zur Laufzeit geprüft
// (ein fehlender Schlüssel oder einer vom falschen Typ löst sofort eine explizite
// Exception aus), während eine falsche TypeScript-Typisierung unbemerkt bleiben kann.
// =========================================================================

// -------------------------------------------------------------------------
// Hülle (Envelope), die allen Serverantworten gemeinsam ist (siehe ServerResponse<T> auf der
// NestJS-Seite und das Interface ServerResponse<T> des Vue.js-Clients).
//
// Dart verallgemeinert ebenfalls mit spitzen Klammern (<T>), genau wie
// TypeScript - der große Unterschied ist, dass hier ein bloßes "as T" nicht
// genügt, um das Feld [data] umzuwandeln: Die Funktion, die aus rohem JSON ein T
// bauen kann, muss mitgegeben werden (der Parameter [parseData]
// unten), da Dart T zur Laufzeit nicht kennt
// (Type Erasure verhindert, direkt "T.fromJson(...)"
// zu schreiben).
// -------------------------------------------------------------------------
class ServerResponse<T> {
  final int status; // 0 = Erfolg, alles andere = Fehler (siehe ResponseStatus auf der Serverseite)
  final T? data;

  ServerResponse({required this.status, required this.data});

  factory ServerResponse.fromJson(
    Map<String, dynamic> json,
    T Function(dynamic rawData) parseData,
  ) {
    final rawData = json['data'];
    return ServerResponse<T>(
      status: json['status'] as int,
      data: rawData == null ? null : parseData(rawData),
    );
  }
}

// Kurses): behandelt die Anmeldung des Benutzers, ruft POST /login auf, behält

// unterscheidet diese Fälle nicht, aus Gründen der Einheitlichkeit über ALLE Plattformen (im
// Web stützt sich derselbe Aufruf auf window.localStorage, aber die Dart-API
// bleibt asynchron, um mit den anderen Zielplattformen identisch zu bleiben). Konkrete
// Folge: Man kann die bereits gespeicherte Sitzung nicht mehr wie auf der Vue.js-Seite lesen,
// BEVOR der Widget-Baum eingehängt wird - es braucht ein [init()],
// das explizit asynchron ist und aus
// lib/main.dart vor runApp(...) aufgerufen (und mit await ABGEWARTET) wird, damit der Anmeldebildschirm nicht

import 'dart:convert';

import 'package:flutter/foundation.dart';
import 'package:http/http.dart' as http;
import 'package:shared_preferences/shared_preferences.dart';

import '../models/appointment_models.dart';
import 'settings_service.dart';

const String _storageKey = 'rdvmedecins.session';

class AuthService extends ChangeNotifier {
  // im Konstruktor entgegengenommen, statt per Flutter-Injection bezogen: In diesem
  // Stadium (siehe lib/main.dart) existiert noch kein Widget, also wäre nichts
  // wie context.read<SettingsService>() möglich - genau
  // derselbe Grund wie der in createAuthStore(settings) auf der
  // Vue.js-Seite (src/main.ts) dokumentierte, das settingsStore ebenfalls als Funktionsparameter
  // erhält, statt über inject().
  final SettingsService settings;

  AuthService(this.settings);

  bool isLoggedIn = false;
  String? login;
  String? name;
  Role? role;
  String? accessToken;

  bool get isAdmin => role == Role.admin;

  // -----------------------------------------------------------------------
  // nur EINMAL in lib/main.dart aufzurufen, VOR runApp(...): liest
  // eine eventuell bei einem früheren Start der
  // Anwendung gespeicherte Sitzung erneut ein - Äquivalent von readStoredSession() auf der Vue.js-Seite, aber
  // explizit asynchron (siehe den Kopf dieser Datei) statt
  // im Konstruktor des Stores selbst aufgerufen.
  // -----------------------------------------------------------------------
  Future<void> init() async {
    try {
      final prefs = await SharedPreferences.getInstance();
      final raw = prefs.getString(_storageKey);
      if (raw == null) {
        return; // keine gespeicherte Sitzung: Wir bleiben "nicht angemeldet", Standardwerte oben
      }
      final session = jsonDecode(raw) as Map<String, dynamic>;
      _applyLocalSession(
        accessToken: session['accessToken'] as String,
        login: session['login'] as String,
        name: session['name'] as String,
        role: Role.fromString(session['role'] as String),
      );
    } catch (_) {
      // shared_preferences kann nicht verfügbar sein oder einen beschädigten
      // Wert enthalten - in diesem Fall betrachten wir, wie auf der Vue.js-Seite (try/catch von
      // readStoredSession()), einfach, dass es keine
      // Sitzung gibt, statt den Start der Anwendung abstürzen zu lassen.
    }

    // runApp(...) in lib/main.dart abgewartet, daher lauscht beim Ausführen dieser Methode noch kein Widget
    // auf diesen ChangeNotifier - eine Benachrichtigung
    // wäre nutzlos (und würde in manchen Debug-Konfigurationen sogar eine Exception auslösen, da ein Flutter-ChangeNotifier
    // notifyListeners() verbietet, solange es noch nicht mindestens einen
    // Listener gibt).
  }

  // Äquivalent von: POST /login   JSON-Body { login, password }
  // -----------------------------------------------------------------------

    final httpResponse = await http.post(
      Uri.parse('${settings.apiBaseUrl}/login'),
      headers: {'Content-Type': 'application/json'},
      body: jsonEncode({'login': login, 'password': password}),
    );

      (data) => LoginResult.fromJson(data as Map<String, dynamic>),
    );

      // Abmelden auf der Anwendungsseite, das oben bereits wirksam ist, nicht verhindern.
    }

  // aktualisiert die reaktiven Felder, OHNE den Speicher anzufassen - verwendet von
  // init() (das den Speicher gerade GELESEN hat, ein erneutes Schreiben ist unnötig).

    required String accessToken,
    required String login,
    required String name,
    required Role role,
  }) {

    this.login = login;
    this.name = name;
    this.role = role;
    isLoggedIn = true;

  // geschrieben); hier sind die beiden Operationen getrennt, weil das Schreiben

  // der Felder SOFORT und synchron erfolgen muss

  // Festplatten-I/O zu warten) - eine Umkehrung der Reihenfolge würde die Aktualisierung
  // der Oberfläche unnötig verzögern.
  Future<void> _applySessionAndPersist(LoginResult result) async {

      accessToken: result.accessToken,
      login: result.login,
      name: result.name,
      role: result.role,
    );
    notifyListeners();

      final prefs = await SharedPreferences.getInstance();

        jsonEncode({
          'accessToken': result.accessToken,
          'login': result.login,
          'name': result.name,
          'role': result.role.asString(),

      );

      // Anwendung IM SPEICHER gültig, auch wenn das dauerhafte Speichern fehlschlägt (Kontingent überschritten,
      // schreibgeschützter Speicher...) - nur ein späterer Neustart der
      // Anwendung würde darunter leiden (der Benutzer müsste sich erneut anmelden).
    }
  }

    // =========================================================================
// core/http/auth_http_client.dart
// -------------------------------------------------------------------------
// Port von core/interceptors/auth.interceptor.ts (Vue.js-Client dieses
// Kurses). Diese Datei tut zwei Dinge, genau wie ihr
// Vue.js-Gegenstück (selbst ein Port der Angular- und React-Clients):
//   1. fügt jeder Anfrage den Header "Authorization: Bearer <token>" hinzu, wenn
//      der Benutzer angemeldet ist (siehe AuthService.accessToken);
//   2. wenn der Server mit 401 antwortet (Token fehlt, ungültig oder abgelaufen),
//      meldet er den Benutzer clientseitig sauber ab.
//
// [fetch] (auf der Vue.js- und React-Seite verwendet) und Angulars [HttpClient] haben
// in Dart KEIN DIREKTES Äquivalent: Das Paket [http] (siehe pubspec.yaml)
// stellt freie Funktionen (http.get(...), http.post(...)) bereit, statt
// eines Objekts, das global abgefangen werden könnte. Der Port bleibt dennoch
// dem GEIST von useAuthFetch() treu: Statt einer Composable-Funktion, die
// ein "erweitertes fetch" liefert, wird hier eine ECHTE KLASSE geschrieben, [AuthHttpClient],
// deren Methoden get(...)/post(...) genau dieselbe Rolle spielen -
// jeder Code, der mit dem Server sprechen will (hier nur
// core/services/appointment_service.dart), ruft DIESE Methoden auf statt direkt das
// Paket http.
//
// Eine Klasse statt einer Composable-Funktion zu schreiben, ist in Dart/Flutter eine natürliche
// Wahl: Anders als ein Vue.js-<script setup> (das
// nur einmal pro Komponenteninstanz läuft, siehe den Kommentar zu
// auth.interceptor.ts), hat ein ChangeNotifier oder eine Dart-Service-Klasse
// keinen "bei jedem Rendern ausgeführten Rumpf", vor dem man sich hüten müsste -
// also braucht es auch hier kein Äquivalent von useCallback(),
// aber aus einem anderen Grund: Es gibt schlicht keine
// Funktion, die "bei jedem Rendern neu erzeugt" wird, da die Klasse
// nur einmal von lib/main.dart gebaut wird (siehe unten).
// =========================================================================

import 'dart:async' show unawaited;

import 'package:http/http.dart' as http;

import '../services/auth_service.dart';

class AuthHttpClient {
  final AuthService auth;
  final http.Client _client = http.Client();

  AuthHttpClient(this.auth);

  Future<http.Response> get(Uri url) => _send(() => _client.get(url, headers: _headers()));

  Future<http.Response> post(Uri url, {required Object body}) => _send(
        () => _client.post(
          url,
          headers: {..._headers(), 'Content-Type': 'application/json'},
          body: body,
        ),
      );

  // baut die Header, die jeder geschützten Anfrage gemeinsam sind - das Äquivalent
  // von "new Headers(options.headers); if (auth.accessToken) {...}" auf der
  // Vue.js-Seite, aber als einfache Map<String, String> (der Typ,
  // den das Paket http erwartet, hier einfacher als eine Klasse Headers).
  Map<String, String> _headers() {
    final accessToken = auth.accessToken;
    return accessToken == null ? {} : {'Authorization': 'Bearer $accessToken'};
  }

  // faktorisiert heraus, was get(...) und post(...) gemeinsam haben: den HTTP-Aufruf
  // ausführen und dann, wenn die Antwort 401 lautet, den Benutzer abmelden - die
  // als Parameter erhaltene Funktion [call] spielt die Rolle der "...options",
  // die auf der Vue.js-Seite von fetch(path, { ...options, headers }) übergeben werden:
  // An dieser Stelle wissen wir noch nicht, ob es ein GET
  // oder ein POST ist, nur dass er ausgeführt und seine Antwort geprüft werden muss.
  Future<http.Response> _send(Future<http.Response> Function() call) async {
    final response = await call();
    // Ein 401 während einer Sitzung bedeutet, dass das Token nicht mehr gültig ist
    // (abgelaufen oder Server neu gestartet): Der Client wird sauber abgemeldet,
    // statt die Anwendung in einem inkonsistenten Zustand zu belassen (dem Anschein nach angemeldet,
    // aber ohne dass noch eine Anfrage gelingt). Es gibt
    // kein "await" auf logOut(): Die HTTP-Antwort (auch eine fehlerhafte)
    // muss an den Aufrufer zurückgegeben werden, ohne auf das Ende des Leerens
    // des lokalen Speichers zu warten, das seinerseits im Hintergrund abgeschlossen wird.
    if (response.statusCode == 401) {
      unawaited(auth.logOut());
    }
    return response;
  }
}

// core/i18n/translations_service.dart
// -------------------------------------------------------------------------
// ZUSAMMENGEFÜHRTER Port von src/i18n.ts (Konfiguration von vue-i18n) UND von
// core/composables/language.composable.ts (Vue.js-Client dieses Kurses).

// vielen Funktionen (Pluralisierung, Datums-/Zahlenformate...),
// die gesamte eigentliche Übersetzungsarbeit leistet; language.composable.ts
// ergänzt lediglich das Speichern der Sprachwahl in
// localStorage. Flutter hat kein direktes Äquivalent zu vue-i18n/react-
// i18next/@ngx-translate/core, das standardmäßig installiert ist: Statt

// the application to mobile, desktop and web"): src/i18n.ts lädt
// jedes Wörterbuch mit einem fetch("/i18n/{language}.json") - eine relative
// URL, die einen WEBSERVER voraussetzt, der die Dateien des Clients ausliefert (Vite in der Entwicklung, ein
// statischer Server nach dem Build). Eine mobile
// oder Desktop-Flutter-Anwendung hat KEINEN WEBSERVER, der sie ausliefert
// : Der Code UND seine statischen Ressourcen (hier die JSON-Dateien) sind
// gemeinsam in ein einziges, auf dem Gerät installiertes Paket EINGEBETTET (.apk,
// .app, .exe...). Deshalb verwendet diese Datei rootBundle.loadString(...)
// - die Flutter-API, die eine im Abschnitt [assets] von
// pubspec.yaml deklarierte Datei direkt aus diesem Paket liest - statt eines Netzwerkaufrufs.
// Auf dem Web-Ziel stützt sich rootBundle im Hintergrund auf eine echte HTTP-Anfrage
// an die neben der Anwendung veröffentlichten Dateien, aber dieses Detail
// bleibt hier unsichtbar: Derselbe Dart-Code funktioniert ohne jede Plattformbedingung
// in den 3 Umgebungen - genau das zentrale Argument dieses
// Kapitels.
// =========================================================================

import 'dart:convert';

import 'package:flutter/foundation.dart';
import 'package:flutter/services.dart' show rootBundle, ServicesBinding;
import 'package:shared_preferences/shared_preferences.dart';

const String _storageKey = 'rdvmedecins.language';
final String _defaultLanguage = ServicesBinding.instance.platformDispatcher.locale.languageCode == 'fr' ? 'fr' : 'en';

class TranslationsService extends ChangeNotifier {
  String currentLanguage = _defaultLanguage;

  // bereits geladene Wörterbücher (vermeidet das erneute Lesen einer schon gesehenen Asset-Datei
  // während der Sitzung) - dieselbe Optimierung wie loadedDictionaries auf der
  // Vue.js-Seite (src/i18n.ts), aber hier wird das dekodierte Wörterbuch selbst aufbewahrt
  // statt eines einfachen Sets bereits gesehener Sprachen: Vue.js konnte sich mit einem Set begnügen,
  // weil vue-i18n SELBST die geladenen Wörterbücher
  // im Speicher hält (setLocaleMessage); da hier keine entsprechende
  // Bibliothek existiert, muss diese Cache-Rolle direkt von dieser
  // Datei übernommen werden.
  final Map<String, Map<String, dynamic>> _dictionaries = {};

  // -----------------------------------------------------------------------
  // nur EINMAL in lib/main.dart aufzurufen, VOR runApp(...):
  // stellt die bei einem früheren Start gespeicherte Sprache wieder her (falls
  // vorhanden) und lädt ihr Wörterbuch - Äquivalent des letzten Blocks von
  // createLanguageStore() auf der Vue.js-Seite (das Lesen von savedLanguage in
  // localStorage), aber aus denselben Gründen, die bereits in core/services/auth_service.dart dokumentiert sind,
  // explizit asynchron gemacht
  // (shared_preferences ist IMMER asynchron, anders als
  // localStorage).
  // -----------------------------------------------------------------------
  Future<void> init() async {
    String startLanguage = _defaultLanguage;
    try {
      final prefs = await SharedPreferences.getInstance();
      startLanguage = prefs.getString(_storageKey) ?? _defaultLanguage;
    } catch (_) {
      // keine lesbare Einstellung: in der Standardsprache starten (Englisch oder
      // Französisch auf einem französischen Gerät), wie auf der Vue.js-Seite.
    }
    await _loadDictionary(startLanguage);
    currentLanguage = startLanguage;
    // kein notifyListeners() hier, aus demselben Grund wie in
    // AuthService.init(): Diese Methode wird vor
    // runApp(...) abgewartet, daher lauscht noch kein Widget auf diesen ChangeNotifier.
  }

  // Äquivalent von: changeLanguage(language) auf der Vue.js-Seite (ausgelöst durch die
  // FR/EN-Buttons von lib/app.dart, siehe weiter hinten in diesem Kapitel).
  // -----------------------------------------------------------------------
  Future<void> changeLanguage(String language) async {
    if (language == currentLanguage) {
      return;
    }
    await _loadDictionary(language);
    currentLanguage = language;
    notifyListeners(); // hier hingegen läuft die Anwendung bereits: Wir benachrichtigen
    try {
      final prefs = await SharedPreferences.getInstance();
      await prefs.setString(_storageKey, language);
    } catch (_) {
      // Der Sprachwechsel bleibt für diesen Lauf wirksam, auch wenn das
      // Speichern fehlschlägt - nur ein späterer Neustart würde darunter leiden.
    }
  }

  // -----------------------------------------------------------------------
  // Äquivalent von: loadDictionary(language) auf der Vue.js-Seite - dasselbe
  // Caching-Prinzip (loadedDictionaries), aber mit Lesen eines eingebetteten
  // Assets statt eines Netzwerk-fetch() (siehe den Kopf dieser Datei).
  // -----------------------------------------------------------------------
  Future<void> _loadDictionary(String language) async {
    if (_dictionaries.containsKey(language)) {
      return; // bei einem früheren Sprachwechsel bereits geladen
    }
    final content = await rootBundle.loadString('assets/i18n/$language.json');
    _dictionaries[language] = jsonDecode(content) as Map<String, dynamic>;
  }

  // -----------------------------------------------------------------------
  // die Übersetzungsfunktion selbst - von den Widgets als t('LOGIN.TITLE') aufgerufen
  // (siehe lib/features/...), genau wie t('LOGIN.TITLE')
  // auf der Vue.js-Seite (useI18n().t). Der Schlüssel ist "gepunktet" (ein Punkt trennt
  // jede Ebene): Wir steigen also Segment für Segment in das verschachtelte JSON-Wörterbuch
  // hinab, statt das Wörterbuch ein für alle Mal
  // zu verflachen, wie vue-i18n es intern tut - eine Wahl, die für die Größe dieser beiden Wörterbücher
  // völlig ausreicht.
  // -----------------------------------------------------------------------
  String t(String key) {
    final dictionary = _dictionaries[currentLanguage];
    if (dictionary == null) {
      return key; // Wörterbuch noch nicht geladen: Als letzter Ausweg wird der Schlüssel selbst angezeigt
    }
    dynamic currentValue = dictionary;
    for (final segment in key.split('.')) {
      if (currentValue is Map<String, dynamic> && currentValue.containsKey(segment)) {
        currentValue = currentValue[segment];
      } else {
        return key; // Schlüssel nicht gefunden: derselbe Fallback wie oben
      }
    }
    return currentValue is String ? currentValue : key;
  }
}

// ändert, OHNE jeden Begriff eines "Widgets mit oder ohne Zustand". Flutter unterscheidet
// explizit zwei Arten von Widgets: StatelessWidget (nichts ändert sich je

import 'package:provider/provider.dart';

import '../../core/i18n/translations_service.dart';
import '../../core/services/auth_service.dart';

class LoginPage extends StatelessWidget {

  Widget build(BuildContext context) {
    return const _LoginForm();
  }
}

class _LoginForm extends StatefulWidget {
  const _LoginForm();

  @override
  State<_LoginForm> createState() => _LoginFormState();
}

class _LoginFormState extends State<_LoginForm> {
  // TextEditingController: Anders als v-model="login" auf der Vue.js-Seite
  // (das ein Feld direkt in beide Richtungen an ein ref bindet, in einem
  // einzigen Attribut), hat Flutter kein in das
  // Widget TextField eingebautes Two-Way-Binding - man muss explizit einen Controller besitzen,
  // ihn lesen (controller.text) und FREIGEBEN (dispose()), sobald das Widget
  // zerstört wird, siehe dispose() unten. Das ist einmalig aufwendiger zu schreiben,
  // macht aber einen Lebenszyklus explizit (Erzeugung -> Lesen -> Freigabe
  // der Ressourcen), den Vue.js für ein ref selbst im Hintergrund verwaltet.
  final TextEditingController _loginController = TextEditingController();
  final TextEditingController _passwordController = TextEditingController();

  bool _submitting = false;
  String? _error;

  @override
  void dispose() {
    // gibt die den Controllern zugeordneten Ressourcen frei - das Vergessen würde
    // bei jeder Neuerstellung dieses Bildschirms ein Speicherleck verursachen.
    // Vue.js, dessen ref() einfache JavaScript-Objekte sind, die wie jedes andere Objekt vom Garbage Collector
    // eingesammelt werden,
    // kennt keinen solchen vorzusehenden Schritt.
    _loginController.dispose();
    _passwordController.dispose();
    super.dispose();
  }

  Future<void> _onSubmit() async {
    final login = _loginController.text.trim();
    final password = _passwordController.text;
    if (login.isEmpty || password.isEmpty) {
      return;
    }
    setState(() {
      _error = null;
      _submitting = true;
    });
    try {
      // context.read<AuthService>(): ein "einmaliges" Lesen, OHNE erneutes Abonnieren
      // künftiger Änderungen (anders als context.watch<...>(), siehe

      // aktuell bleiben muss. Es ist das Flutter/provider-Äquivalent von

      // zwischen einmaligem Lesen und erneutem Abonnieren nicht: useAuth() liefert immer

            child: Column(

                  const SizedBox(height: 16),
                ],
                TextField(
                  controller: _loginController,
                  decoration: InputDecoration(labelText: t('LOGIN.LOGIN_LABEL')),
                  textInputAction: TextInputAction.next,
                ),
                const SizedBox(height: 12),
                TextField(
                  controller: _passwordController,
                  decoration: InputDecoration(labelText: t('LOGIN.PASSWORD_LABEL')),
                  obscureText: true,
                  textInputAction: TextInputAction.done,
                  // onSubmitted: ausgelöst durch die Taste "Enter" (oder ihr
                  // Äquivalent auf der virtuellen Smartphone-Tastatur) - das Gegenstück zu
                  // @submit.prevent am Tag <form> auf der Vue.js-Seite,
                  // hier direkt am LETZTEN Feld des Formulars platziert.
                  onSubmitted: (_) => _onSubmit(),
                ),
                const SizedBox(height: 20),

// Port von src/app/features/doctor-day-picker/DoctorDayPicker.vue (Vue.js-
// Client dieses Kurses): das Widget zur Auswahl eines Arztes und eines
// Tages, um dann dessen Terminkalender anzufordern.

// Ausgaben) wird hier ganz direkt zu einem Dart-KONSTRUKTOR: Die Props
// sind die benannten Parameter des Konstruktors (doctors, onSearch), und
// ein "Ereignis auszulösen" wird einfach zum AUFRUF der als
// Parameter erhaltenen Funktion - genau die Wahl, die bereits der React-Client
// dieses Kurses getroffen hat (eine Funktions-Prop, onSearch), statt der
// für Vue.js spezifischen expliziten Deklaration [defineEmits]. Flutter macht wie React
// KEINEN syntaktischen Unterschied zwischen "normaler Prop" und "Prop zum
// Benachrichtigen des Elternteils": Es ist eine Funktion wie jede andere, die vom

import 'package:flutter/material.dart';
import 'package:intl/intl.dart';
import 'package:provider/provider.dart';

import '../../core/i18n/translations_service.dart';
import '../../core/models/appointment_models.dart';

// Format "yyyy-MM-dd" - dasselbe Datumsformat wie auf der Vue.js-Seite
// (new Date().toISOString().slice(0, 10)), aber hier explizit über das Paket intl
// gebaut statt durch Abschneiden des Strings: Dart-DateTime
// hat keine eingebaute Methode toISOString().
final DateFormat _dayFormat = DateFormat('yyyy-MM-dd');

class DoctorDayPicker extends StatefulWidget {
  final List<Doctor> doctors;

  // onSearch(doctorId, day): das direkte Äquivalent von
  // "search: [criteria: { doctorId: number; day: string }]" auf der
  // Vue.js-Seite - hier zwei Positionsparameter statt eines einzelnen Objekts
  // {doctorId, day}, eine in Dart ebenso gültige Wahl wie die andere.
  final void Function(int doctorId, String day) onSearch;

  const DoctorDayPicker({super.key, required this.doctors, required this.onSearch});

  @override
  State<DoctorDayPicker> createState() => _DoctorDayPickerState();
}

class _DoctorDayPickerState extends State<DoctorDayPicker> {
  // rein lokaler Zustand dieses Widgets (was in den Menüs ausgewählt ist,
  // solange der Benutzer den Button nicht angeklickt hat) - das direkte
  // Äquivalent von selectedDoctorId/selectedDay auf der Vue.js-Seite, als
  // einfache Felder von _DoctorDayPickerState statt ref(...): Ein
  // Flutter-StatefulWidget braucht für
  // ein lokales Feld keine besondere "Umhüllung", setState(...) (siehe _onDoctorChoice unten) genügt,
  // um zu signalisieren, dass ein Neuzeichnen nötig ist.
  int? _selectedDoctorId;
  DateTime _selectedDay = DateTime.now();

  Future<void> _pickDay() async {
    // Flutter hat kein direktes Äquivalent zu <input type="date"> (ein
    // Datumseingabe-Widget, das NATIV IM BROWSER vorhanden ist und von dem Vue.js
    // im Web profitieren konnte): In den 3 von diesem Client anvisierten Umgebungen
    // (mobil, Desktop, Web) zeichnet Flutter SELBST den
    // Datumsauswahldialog (showDatePicker(...) unten) - ein
    // Material-Widget, das in den 3 Zielumgebungen gleich aussieht. Es ist eine
    // sehr konkrete Veranschaulichung des Versprechens "eine einzige Codebasis für 3
    // Umgebungen": Wo Vue.js sich auf einen Baustein
    // des Browsers stützte (der auf Mobilgeräten und Desktop fehlt), liefert Flutter seinen
    // eigenen Baustein, der ÜBERALL verfügbar ist.
    final picked = await showDatePicker(
      context: context,
      initialDate: _selectedDay,
      firstDate: DateTime(2020),
      lastDate: DateTime(2100),
    );
    if (picked != null) {
      setState(() => _selectedDay = picked);
    }

  void _onSearchClick() {

    if (doctorId == null) {
      return; // der Button ist in diesem Fall ohnehin deaktiviert (siehe build() unten)

// canEdit: Wenn false (Rolle USER), verschwinden die Buttons "Book"/"Cancel" -
// der Terminkalender kann weiterhin eingesehen werden, aber nur lesend (der
// Server würde diese Aktionen für einen USER ohnehin verweigern, 403 Forbidden,
// siehe RolesGuard auf der Serverseite).
//
// [v-if]/[v-else] und [v-for] (Vue.js) werden hier zu GEWÖHNLICHEN Dart-Ausdrücken:
// Flutter kennt, wie zuvor React (siehe den Kommentar zu
// Schedule.vue), KEINE von der Programmiersprache getrennte "Template-Sprache" -
// const/if/for und die Operatoren ?./?? von normalem Dart
// genügen, um Bedingungen und Listen direkt in der
// Methode build(...) unten auszudrücken.

import 'package:flutter/material.dart';
import 'package:provider/provider.dart';

import '../../core/i18n/translations_service.dart';
import '../../core/models/appointment_models.dart';

class ScheduleView extends StatelessWidget {
  final DoctorDaySchedule? schedule;
  final bool canEdit;
  final void Function(SlotJson slot) onBook;
  final void Function(AppointmentJson appointment) onCancel;

  const ScheduleView({
    super.key,
    required this.schedule,
    required this.canEdit,
    required this.onBook,
    required this.onCancel,
  });

  // kleine Formatierungs-Hilfsfunktion, "8:05" statt "8:5" -
  // vom Geist her identisch mit formatTime(...) auf der Vue.js-Seite.
  static String _formatTime(int h, int m) => '$h:${m.toString().padLeft(2, '0')}';

  void _onSlotClick(DoctorDaySlot daySlot) {
    if (!canEdit) {
      return; // Der Button wird in diesem Fall ohnehin nicht angezeigt (siehe build() unten)
    }
    final appointment = daySlot.appointment;
    if (appointment == null) {
      onBook(daySlot.slot); // freier Slot: Buchung anbieten
    } else {
      onCancel(appointment); // bereits gebuchter Slot: Stornierung des bestehenden Termins anbieten
    }
  }

  @override
  Widget build(BuildContext context) {
    final t = context.watch<TranslationsService>().t;
    final schedule = this.schedule;

    if (schedule == null) {
      return Padding(
        padding: const EdgeInsets.symmetric(vertical: 24),
        child: Text(
          t('SCHEDULE.EMPTY_STATE'),
          style: TextStyle(color: Theme.of(context).colorScheme.outline),
        ),
      );
    }

    return Card(
      child: Padding(
        padding: const EdgeInsets.all(16),
        child: Column(
          crossAxisAlignment: CrossAxisAlignment.start,
          children: [
            Text(
              '${t('SCHEDULE.TITLE_PREFIX')} ${schedule.day} - ${schedule.doctor.title} '
              '${schedule.doctor.firstName} ${schedule.doctor.lastName}',
              style: Theme.of(context).textTheme.titleMedium,
            ),
            const SizedBox(height: 12),
            // DataTable: das Flutter-Material-Äquivalent der HTML-<table>
            // von Schedule.vue - anders als bei HTML müssen ihre Zeilen
            // in Dart explizit über .map(...).toList() gebaut werden
            // (auch hier das Äquivalent von v-for="daySlot in
            // schedule.slots" :key="daySlot.slot.id" - die DataRow
            // braucht keinen expliziten "key" wie in Vue.js/React: Die
            // Liste wird bei jedem Rendern vollständig neu aufgebaut, Flutter versucht hier nicht,
            // vorhandene Zeilen wiederzuverwenden).
            SingleChildScrollView(
              scrollDirection: Axis.horizontal,
              child: DataTable(
                columns: [
                  DataColumn(label: Text(t('SCHEDULE.COLUMN_SLOT'))),
                  DataColumn(label: Text(t('SCHEDULE.COLUMN_STATUS'))),
                  const DataColumn(label: Text('')),
                ],
                rows: schedule.slots.map((daySlot) {
                  final appointment = daySlot.appointment;
                  final slot = daySlot.slot;
                  return DataRow(
                    // leicht getönter Hintergrund für einen freien Slot - das
                    // Gegenstück zur CSS-Klasse "free-slot" auf der Vue.js-Seite.
                    color: appointment == null
                        ? WidgetStateProperty.all(Theme.of(context).colorScheme.surfaceContainerLow)
                        : null,
                    cells: [
                      DataCell(Text(
                        '${_formatTime(slot.startHour, slot.startMinute)} - '
                        '${_formatTime(slot.endHour, slot.endMinute)}',
                      )),
                      DataCell(
                        appointment == null
                            ? Chip(
                                label: Text(t('SCHEDULE.FREE')),
                                backgroundColor: Colors.green.shade100,
                              )
                            : Chip(
                                label: Text('${appointment.client?.title ?? ''} ${appointment.client?.firstName ?? ''} ${appointment.client?.lastName ?? ''}'),
                              ),
                      ),
                      DataCell(
                        // canEdit: false für eine Rolle USER (nur lesend)
                        canEdit
                            ? OutlinedButton(
                                onPressed: () => _onSlotClick(daySlot),
                                child: Text(appointment == null ? t('SCHEDULE.BOOK') : t('SCHEDULE.CANCEL_APPOINTMENT')),
                              )
                            : const SizedBox.shrink(),
                      ),
                    ],
                  );
                }).toList(),
              ),
            ),
          ],
        ),
      ),
    );
  }
}

// features/booking_dialog/booking_dialog.dart
// -------------------------------------------------------------------------
// Port von src/app/features/booking-dialog/BookingDialog.vue (Vue.js-
// Client dieses Kurses): das (modale) Fenster zur Auswahl eines
// Patienten, um einen freien Slot zu buchen.
//
// WICHTIGER STRUKTURELLER UNTERSCHIED zu Vue.js (und zu den drei anderen
// Widgets von lib/features/): BookingDialog.vue ist eine Komponente, die IMMER
// im Baum VORHANDEN ist und deren Prop [open] (ein von
// App.vue gehaltener Boolean) lediglich die Anzeige steuert (v-if="open") - GENAU dieselbe
// Wahl wie bei den Angular- und React-Clients dieses Kurses, motiviert durch das Anliegen,
// Vue.js und das JavaScript von Bootstrap daran zu hindern, um
// dieselbe Information zu streiten ("ist das Modal geöffnet?").
//
// Flutter hat dieses Problem nicht: Ein Dialogfeld IST KEIN Widget,
// das im Baum bedingt ein- oder ausgeblendet wird, sondern eine ECHTE
// SEITE, die beim Öffnen mit showDialog(...) auf den Navigationsstapel
// (den Navigator) gelegt
// und beim Schließen automatisch wieder entfernt wird. Es gibt hier also WEDER einen Zustand "open: bool" im
// Eltern-Widget (siehe lib/app.dart, das kein Feld hat, das
// slotBeingBooked auf der Vue.js-Seite entspricht), NOCH Ereignisse "confirm"/"close", die
// auszulösen wären: showDialog(...) liefert ein Future, das mit dem
// an Navigator.pop(...) übergebenen Wert abgeschlossen wird - null, wenn der Benutzer
// ohne Auswahl geschlossen hat, andernfalls die ID des gewählten Patienten. Es ist das
// AUFRUFENDE Widget (lib/app.dart), das dieses Future abwartet, um zu wissen, was
// danach zu tun ist - eine vollständige Umkehrung der Kommunikationsrichtung
// im Vergleich zu den beiden Vue.js-Ereignissen.
// =========================================================================

import 'package:flutter/material.dart';
import 'package:provider/provider.dart';

import '../../core/i18n/translations_service.dart';
import '../../core/models/appointment_models.dart';

// -----------------------------------------------------------------------
// Hilfsfunktion: öffnet das Dialogfeld und liefert die ID des
// gewählten Patienten zurück (oder null, wenn der Benutzer abgebrochen/ohne Auswahl geschlossen hat).
// DIESE Funktion ruft lib/app.dart auf - niemals direkt den
// Konstruktor von _BookingDialogContent unten.
// -----------------------------------------------------------------------
Future<int?> openBookingDialog({
  required BuildContext context,
  required SlotJson slot,
  required List<Client> clients,
}) {
  return showDialog<int>(
    context: context,
    builder: (_) => _BookingDialogContent(slot: slot, clients: clients),
  );
}

class _BookingDialogContent extends StatefulWidget {
  final SlotJson slot;
  final List<Client> clients;

  const _BookingDialogContent({required this.slot, required this.clients});

  @override
  State<_BookingDialogContent> createState() => _BookingDialogContentState();
}

class _BookingDialogContentState extends State<_BookingDialogContent> {
  int? _selectedClientId;

  void _onConfirmClick() {
    final clientId = _selectedClientId;
    if (clientId == null) {
      return;
    }
    // Navigator.pop(context, clientId): schließt das Dialogfeld UND
    // übergibt clientId als Ergebnis des von
    // openBookingDialog(...) zurückgegebenen Futures - das Äquivalent, in einem einzigen Aufruf, von
    // emit('confirm', { clientId }) GEFOLGT vom Schließen (implizit,
    // vom Elternteil über [open] gesteuert) auf der Vue.js-Seite.
    Navigator.pop(context, clientId);
  }

  void _onCloseClick() {
    // Navigator.pop(context) ohne zweites Argument: Das von
    // openBookingDialog(...) zurückgegebene Future wird mit null abgeschlossen - das Äquivalent von
    // emit('close') auf der Vue.js-Seite.
    Navigator.pop(context);
  }

  @override
  Widget build(BuildContext context) {
    final t = context.watch<TranslationsService>().t;
    final slot = widget.slot;

    // AlertDialog: das Material-Widget für Dialogfelder -
    // liefert von sich aus bereits den abgedunkelten Hintergrund (das Äquivalent des
    // .modal-backdrop, der auf der Vue.js-Seite "von Hand" gesetzt wurde) und das
    // standardmäßige Schließverhalten (Tippen außerhalb des Feldes, Escape-Taste
    // auf Desktop/Web) - ein Verhalten, das der Vue.js-Client selbst
    // nachbauen musste, da Bootstrap nur einen Teil davon automatisch behandelt.
    return AlertDialog(
      title: Text(t('BOOKING_DIALOG.TITLE')),
      content: Column(
        mainAxisSize: MainAxisSize.min,
        crossAxisAlignment: CrossAxisAlignment.start,
        children: [
          Text(
            '${t('BOOKING_DIALOG.SLOT_FROM')} ${slot.startHour}:${slot.startMinute.toString().padLeft(2, '0')} '
            '${t('BOOKING_DIALOG.SLOT_TO')} ${slot.endHour}:${slot.endMinute.toString().padLeft(2, '0')}',
          ),
          const SizedBox(height: 16),
          DropdownButtonFormField<int>(
            decoration: InputDecoration(labelText: t('BOOKING_DIALOG.PATIENT_LABEL')),
            value: _selectedClientId,
            hint: Text(t('BOOKING_DIALOG.CHOOSE_PATIENT')),
            items: widget.clients
                .map(
                  (client) => DropdownMenuItem(
                    value: client.id,
                    child: Text('${client.title} ${client.firstName} ${client.lastName}'),
                  ),
                )
                .toList(),
            onChanged: (id) => setState(() => _selectedClientId = id),
          ),
        ],
      ),
      actions: [
        TextButton(onPressed: _onCloseClick, child: Text(t('BOOKING_DIALOG.CANCEL'))),
        FilledButton(
          onPressed: _selectedClientId == null ? null : _onConfirmClick,
          child: Text(t('BOOKING_DIALOG.CONFIRM')),
        ),
      ],
    );
  }
}
